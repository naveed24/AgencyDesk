# AgencyDesk — design decisions

**Identity and roles.** `users` stores one global identity per normalized email; `agency_memberships` maps a user to an agency and a **role scoped to that agency**. Thus the same email can be an `agency_admin` for Northstar and a `client_user` for Bluebird without duplicate login records. JWTs carry only `sub`, `agency_id`, and expiration. Every protected API call reloads the membership from PostgreSQL rather than trusting a stale role inside a token.

**Tenant isolation.** Every tenant-owned record carries `agency_id`. Composite foreign keys, such as `projects(agency_id, client_id) → clients(agency_id, id)` and `tasks(agency_id, project_id) → projects(agency_id, id)`, prevent cross-tenant relationships at the database level. All HTTP reads/writes explicitly scope by the authenticated membership's `agency_id`; an ID guessed from another tenant receives a 404. Schema constraints enforce reference integrity; **API checks enforce confidentiality** (a superuser connected directly to a shared database can still read its tables). A production deployment would also use a restricted DB role and consider PostgreSQL RLS as defense in depth.

**Client visibility.** A `client_user` needs an explicit `client_memberships` link to the project's client. For each task, comment, and attachment path, the API verifies agency + project entitlement and the parent task's `is_client_visible` flag. It further filters `is_client_visible` on comments and files. Protected downloads and file reviews repeat these checks, rather than trusting the list endpoint. Dashboard task counts and logged time are calculated only from tasks visible to that viewer. Clients cannot create tasks, change task status, upload files or log time; they can comment on permitted tasks and review visible files.

**Edge cases.** A partial unique index on pending invitations makes concurrent resends an upsert of one invite; acceptance obtains a row lock and safely returns `already_accepted` on retry. When staff are removed from a project, their assigned tasks are unassigned before membership deletion **within one transaction**, so foreign keys never become invalid. Database triggers prevent client-role contacts from being inserted as project staff and vice versa, including inconsistent later role changes. Seeded integration tests exercise cross-tenant access, internal data leaks, same-email multiple roles, invitation retries, and member removal.
